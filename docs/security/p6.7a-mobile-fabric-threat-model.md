# P6.7A Mobile Fabric Threat Model

## Protected assets

- Communication content and metadata
- Pairing tokens and device identifiers
- Exact action payloads and approval tokens
- Notification PendingIntents and RemoteInput actions
- Execution evidence and receipts

## Controls

| Threat | Control |
|---|---|
| Untrusted application floods Nexuss | Exact Android package allowlist and source/package consistency check |
| OTP or credential ingestion | Local and Core-side sensitive-content withholding; sensitive metadata keys removed |
| Stolen bearer token | Android Keystore encryption, HMAC request assertion, two-minute timestamp window and nonce replay cache |
| Action payload changes after approval | Canonical payload SHA-256 and approval token must match |
| Wrong phone approves action | Proposal is bound to one paired device ID and session |
| Silent action execution | Biometric/device-credential approval required before approval is accepted |
| Arbitrary application automation | No AccessibilityService; only four allowlisted platform action kinds |
| Direct background call or SMS | Only ACTION_DIAL and ACTION_SENDTO handoffs are implemented |
| False success claim | Evidence records handoff-opened, dispatch-accepted or provider-delivery scope separately |
| App private-data extraction | No private database, backup, root or filesystem access |

## Residual risk

P6.7A uses the existing private-LAN pairing token plus HMAC assertions. A
production public deployment must replace this with asymmetric Android
Keystore-backed device identity, mutual TLS, attestation, certificate rotation,
remote revocation and secure push. The Android source therefore treats HTTP as
a debug-only private-LAN transport; release builds require HTTPS.
